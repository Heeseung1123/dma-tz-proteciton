# 쉽게 읽는 설명: 컴파일러가 DMA 버퍼와 Secure 데이터의 자리를 정해 주는 방법

이 문서는 **LLVM이나 링커를 잘 모르는 사람**을 위한 설명이다. 코드를 몰라도 "무엇이, 왜, 어떤 순서로" 일어나는지 이해할 수 있게 쓰려고 했다. 구체적인 명령과 파일은 [README.md](README.md)에 있다.

---

## 1. 한 문장 요약

> 컴파일러가 프로그램을 읽고 **"이 변수는 태스크 A의 DMA 버퍼다"**, **"이 Secure 변수는 guard 블록에 둬도 안전하다"**를 스스로 판단한다. 그 결과대로 링커가 메모리 자리를 정하고, Secure 부팅 코드가 그 자리에 보호 설정을 건다. 사람이 주소를 손으로 적을 일이 없어진다.

## 2. 왜 필요한가

지금까지는 이런 줄이 코드에 직접 적혀 있었다.

```c
#define DMA_TASK_A_CLUSTER_BASE   0x2001b700u     /* 태스크 A 의 DMA 영역 */
#define DMA_TASK_A_GUARD_BASE     0x2001b800u     /* 그 바로 뒤 보호 블록 */
```

이 방식에는 문제가 세 가지 있다.
- 버퍼를 하나 추가하거나 크기를 바꾸면 **사람이 주소를 다시 계산**해야 한다.
- NS 쪽 주소와 Secure 쪽 설정이 **서로 다른 파일에 따로** 적혀 있다. 하나만 고치면 보호가 어긋난다.
- 태스크가 늘어나거나 공유 버퍼가 생기면 손으로 관리하기 어렵다.

그래서 **"어떤 변수가 DMA 버퍼인지"를 프로그램 코드에서 자동으로 알아내고, 주소는 도구가 정하게** 만든다.

## 3. 배경지식: 프로그램이 만들어지는 과정

### 3.1 두 단계: 컴파일과 링크

```
 app.c ──컴파일러──▶ app.o ─┐
 hal.c ──컴파일러──▶ hal.o ─┼──링커──▶ ns.elf (보드에 올리는 최종 이미지)
 rtos.c ─컴파일러──▶ rtos.o ┘
```

| 단계 | 하는 일 | 비유 |
|---|---|---|
| **컴파일** | C 파일 하나를 기계어 조각(`.o`)으로 바꾼다. 이 시점에는 변수의 **최종 주소가 아직 없다** | 이삿짐을 상자에 담고 상자에 이름표만 붙이는 단계 |
| **링크** | 조각들을 모아 하나로 합치고, 모든 변수와 함수에 **실제 메모리 주소**를 정한다 | 상자들을 새 집의 어느 방에 둘지 정하는 단계 |

### 3.2 섹션: 상자에 붙는 이름표
컴파일러는 결과물을 **이름 붙은 덩어리(섹션)**로 나눈다. 예를 들어 코드는 `.text`, 0으로 시작하는 변수는 `.bss`에 담는다. 링커는 이 **이름을 보고** 자리를 정한다.

그래서 어떤 변수를 원하는 곳에 두고 싶으면, 그 변수에 **특별한 섹션 이름**을 붙이면 된다. 예를 들어 태스크 A의 DMA 버퍼에는 `.dma.t.vDmaTaskA`를 붙인다.

### 3.3 링커 스크립트: 배치 지시서
링커에게 "어떤 이름의 상자를 메모리 어디에 두어라"라고 알려 주는 파일이다(`.ld`). 예를 들면 다음과 같다.

```ld
.dma_c0 : ALIGN(256) {          /* 256 의 배수 주소에서 시작 */
    *(.dma.t.vDmaTaskA)         /* 이 이름표가 붙은 것들을 전부 여기에 */
    . = . + 0x100;              /* 그리고 256 B 를 비워 둔다 (= guard 자리) */
} > RAM
```

### 3.4 심볼: 링커가 정한 주소를 다른 곳에서 읽는 방법
링커 스크립트에서 `__dmac0_start = .;`라고 쓰면 "지금 위치의 주소"에 이름이 붙는다. C 코드는 이 이름을 변수처럼 참조할 수 있고, 링커가 실제 주소로 채워 준다. 이 방법으로 **"링크해 봐야 아는 주소"를 다른 코드에 넘긴다.**

## 4. LLVM이란

### 4.1 컴파일러의 중간 단계
컴파일러는 C 코드를 바로 기계어로 바꾸지 않는다. 그 사이에 **중간 언어**를 거친다.

```
 C 코드 ──(clang)──▶ LLVM IR (중간 언어) ──(최적화·분석)──▶ 기계어
```

- **clang**: C를 읽어 IR로 바꾸는 부분이다.
- **LLVM IR**: 모든 함수, 변수, 함수 호출이 단순하고 규칙적인 형태로 적힌 "공통 중간 언어"다. 예를 들어 `dma_start(rxA, 64)`는 IR에서 이렇게 보인다.
  ```llvm
  call void @dma_start(ptr @rxA, i32 64)     ; rxA 의 주소를 넘기는 호출
  ```
- 사람이 읽기엔 C보다 길지만, **프로그램이 분석하기에는 훨씬 쉽다.** 호출 관계와 변수 사용이 모두 명시적으로 드러나기 때문이다.

### 4.2 Pass: IR을 읽고 판단하는 작은 프로그램
**pass**는 IR을 입력으로 받아 무언가를 하는 작은 프로그램이다. 컴파일러의 최적화도 사실 수십 개 pass의 모음이다.

우리는 pass를 **직접 두 개** 만들어서 컴파일러 안에 끼워 넣는다. 빌드된 pass 파일(`.so`)은 **플러그인**이라서, LLVM 본체를 다시 빌드할 필요가 없다.

### 4.3 LTO: 프로그램 전체를 한 번에 보기
보통은 파일 하나씩 따로 컴파일한다. 그런데 우리의 질문은 여러 파일에 걸쳐 있다.
- "태스크 A(`app_freertos.c`)가 부르는 함수(`app_dma.c`)가 넘기는 버퍼(`buffers.c`)"

**LTO(Link Time Optimization)**를 켜면 컴파일러가 각 파일을 IR 상태로 두었다가, **링크하는 순간 모든 파일의 IR을 하나로 합친다.** 우리 pass는 바로 그때 실행되어 **프로그램 전체**를 본다. 링커 이름은 `ld.lld`이고, LLVM의 링커다.

## 5. 이 프로젝트가 하는 일, 단계별로

### 5.1 NS 쪽: DMA 버퍼 찾기와 배치 (`DmaCluster` pass)

**pass가 하는 질문과 방법**

| 질문 | 방법 (쉬운 말) |
|---|---|
| 태스크는 무엇이 있나? | `xTaskCreate(…)` 호출을 찾아 첫 인자로 넘긴 **태스크 함수**를 모은다 |
| 각 태스크가 실행할 수 있는 함수는? | 태스크 함수에서 시작해 "누가 누구를 부르는지"를 끝까지 따라간다 |
| DMA를 시작하는 곳은? | 설정 파일에 적은 함수(`SECURE_dma_m2m_start` 등)를 부르는 곳을 찾는다 |
| 거기 넘긴 버퍼는 어느 변수인가? | 인자를 **거꾸로 추적**한다. 배열 원소 주소 계산을 벗기고, 다른 함수의 인자로 넘어온 것이면 그 함수를 부른 쪽으로 올라간다 |
| 그 버퍼를 쓰는 태스크는? | 태스크 하나면 그 태스크 전용, 여럿이면 공유 버퍼 |

**pass가 하는 행동**
- 찾은 변수에 섹션 이름표를 붙인다. 태스크 전용이면 `.dma.t.<태스크>`, 공유면 `.dma.s.<번호>`다.
- 결과를 `dma_layout.json`에 기록한다. 어떤 cluster에 어떤 버퍼가 몇 바이트 있는지가 들어 있다.

**그다음 생성기(`gen_layout.py`)가 하는 일**
- JSON을 읽어 **링커 스크립트를 자동으로 만든다.** cluster마다 "256 B 경계에서 시작 → 버퍼들 → 256 B guard 자리"를 배치한다.
- **manifest**(목록표)를 만든다. 링크 후 cluster와 guard의 실제 주소가 여기 채워진다.
- 각 태스크의 NS-MPU 설정 매크로를 만든다. 태스크가 자기 DMA 버퍼에 CPU로 접근할 수 있게 하는 설정이다.

### 5.2 Secure 부팅: 보호 설정 (`secure_dma_boot.c`)
보드가 켜지면 Secure 코드가 NS보다 먼저 실행된다.
1. NS 이미지 안의 manifest를 읽고, 내용이 올바른지 검사한다. 정렬, 범위, 겹침, 개수를 본다.
2. cluster마다 **S-MPU 태그**를 건다. 이것은 "여기는 DMA 허용 영역"이라는 하드웨어 표시이고, Mediator가 TTT 명령으로 확인한다.
3. cluster 바로 뒤 256 B를 **MPCBB guard(Secure 블록)**로 만든다. DMA가 버퍼 끝을 넘어 쓰면 여기서 막힌다.
4. 이후로는 표가 없어도 **하드웨어 설정 자체가 정책**이 된다.

### 5.3 Secure 데이터를 guard에 두기 (`SecureGuardSelect` pass + `pack_guards.py`)

**아이디어**
- guard 블록은 "DMA가 넘어오면 막는 벽"이다. **벽 안쪽 공간은 원래 비어 있다.**
- 이 블록들은 Secure 메모리이므로 **Secure 변수를 보관하는 데 쓸 수 있다.** NS는 읽을 수도 쓸 수도 없고, DMA overflow를 막는 역할도 그대로 유지된다.

**어려운 점은 아무 변수나 옮길 수 없다는 것이다.**
- guard는 부팅 중 `dma_boot_config()`가 실행된 **뒤에야** Secure가 된다. 그 전에는 NS 메모리다.
- 그래서 **부팅 초기에 쓰이는 변수를 옮기면, 그 순간 Secure 데이터가 NS 메모리에 놓인다.**

**pass가 하는 판단**

Secure 프로그램 전체 IR을 보고, 변수마다 다음 조건을 확인한다.

| 확인 | 이유 |
|---|---|
| 0으로 시작하는 변수인가? (`.bss`) | guard에는 초기값을 담아 둘 수 없으므로 부팅 후 0으로 지운다 |
| 256 B 이하인가? | guard 블록들은 서로 떨어져 있어서, 한 변수가 두 블록에 걸칠 수 없다 |
| **부팅 경로에서 쓰이지 않는가?** | `main`에서 `dma_boot_config()`가 끝나기 **전에** 실행될 수 있는 모든 함수를 모은 뒤, 그 함수들이 이 변수를 건드리면 탈락시킨다 |
| 이름이 GCC 쪽과 대응되는가? | Secure 실제 빌드는 GCC가 하므로, GCC 섹션 이름(`.bss.<이름>`)으로 찾을 수 있어야 한다 |

기본 모드는 **개발자가 표시한 변수만** 옮긴다. 다음과 같이 표시하면 pass가 안전한지 검사하고, 안전하지 않으면 **오류**를 낸다.

```c
static evt_record_t s_evt_log[8] __attribute__((annotate("guard")));
```

**배치기(`pack_guards.py`)가 하는 일: 흩어진 상자에 짐 나눠 담기**
1. NS 최종 이미지에서 guard 블록 주소를 모두 읽는다. 이 블록들은 메모리 여기저기 떨어져 있다.
2. 각 블록을 **256 B짜리 상자**로 본다.
3. **큰 짐부터, 들어갈 수 있는 첫 상자에** 넣는다(First-Fit Decreasing).
4. 어느 상자에도 맞지 않는 짐은 **원래 자리(일반 Secure RAM)에 그대로 둔다.**
5. 결과를 Secure 링커 스크립트 조각으로 만든다. "변수 `s_evt_log`는 주소 0x3001BB00 상자에" 같은 지시가 들어간다.

```
guard @0x3001BB00 : s_evt_log(128) s_reject_ring(64) s_dma_stats(32)   224/256 B
guard @0x3001C400 : s_tzic_last(96)                                     96/256 B
옮기지 않음: s_big_table(512 B) — 남은 칸에 맞지 않음
```

**부팅 시 안전장치 (`secure_guard_bind.c`)**
- NS 이미지만 다시 빌드되어 guard 위치가 바뀌면, Secure는 **예전 주소**에 변수를 두고 있게 된다. 그 주소는 이제 NS 메모리일 수 있다.
- 그래서 부팅할 때 **"Secure가 기대하는 guard 주소"와 "manifest의 실제 guard 주소"를 비교**하고, 다르면 즉시 실패로 처리한다(정지).
- 같으면 guard의 Secure 변수들을 0으로 지우고 사용을 시작한다.

## 6. 전체 빌드 순서와 그 이유

```
⓪ Secure 0차 빌드 (GCC)      — NS 가 Secure 함수를 부를 때 쓰는 "입구 주소표"(implib) 생성
① NS 빌드 (clang + LTO)      — 1차 링크(분석) → 생성기 → 2차 링크(확정)  ⇒ guard 주소 확정
② Secure 분석 (clang, 분석만) — guard 로 옮겨도 되는 Secure 변수 고르기
③ 배치기                     — 변수들을 guard 상자에 나눠 담는 링커 스크립트 생성
④ Secure 최종 빌드 (GCC)     — 그 스크립트로 링크. 입구 주소표는 ⓪과 똑같이 유지
⑤ 보드 부팅                  — 주소 일치 검사 → S-MPU / MPCBB 설정 → Secure 변수 초기화
```

**왜 NS를 두 번 링크하나?**
- 링커 스크립트를 만들려면 분석 결과가 필요하다.
- 그런데 분석은 링크하는 동안(LTO) 일어난다.
- 그래서 한 번 링크해서 분석 결과를 얻고, 그 결과로 만든 스크립트로 **다시 링크**한다. 두 번째 링크의 분석 결과가 첫 번째와 같은지도 자동으로 비교한다.

**왜 Secure를 두 번 빌드하나?**
- NS는 Secure 함수의 입구 주소가 필요하고, Secure는 NS가 정한 guard 주소가 필요하다. 서로가 서로를 필요로 하는 셈이다.
- **입구 주소를 고정하는 옵션(`--in-implib`)**으로 이 순환을 끊는다. 그러면 Secure를 다시 빌드해도 입구 주소가 그대로라서 NS를 다시 빌드할 필요가 없다.

**왜 Secure는 GCC 그대로인가?**
- Secure에서는 "분석"만 LLVM으로 하면 되기 때문이다.
- 실제 바이너리는 기존 GCC 빌드를 그대로 쓰고, 링커 스크립트 조각만 추가한다. 바꾸는 범위가 가장 작다.

## 7. 예시로 따라가기

### 7.1 DMA 버퍼 `s_dmaDstA` 하나의 여정
1. 소스에 `static uint8_t s_dmaDstA[64];`가 있고, 태스크 A가 `SECURE_dma_m2m_start(src, s_dmaDstA, 64)`를 부른다.
2. 링크(LTO) 중에 **DmaCluster pass**가 이 호출을 찾는다. 두 번째 인자가 `s_dmaDstA`이고, 이 호출이 태스크 A에서만 일어나므로 섹션 `.dma.t.vDmaTaskA`를 붙인다.
3. **생성기**가 "cluster 0 = `.dma.t.vDmaTaskA`, 크기 256 B, 그 뒤 guard 256 B"라는 링커 스크립트를 만든다.
4. **2차 링크**에서 링커가 주소를 정한다. 예를 들어 cluster 0x2001B700, guard 0x2001B800이다. 이 주소는 manifest에 기록된다.
5. **Secure 부팅**이 manifest를 읽는다. 0x2001B700~0x2001B7FF에 S-MPU 태그를 걸고, 0x2001B800 블록을 MPCBB Secure로 만든다.
6. 실행 중에 Mediator가 dst를 검사한다.
   - TTT가 "S-MPU 태그 영역 안인가"를 본다.
   - TTAT가 "태스크 A가 쓸 수 있는가"를 본다.
   - 둘 다 통과하면 DMA를 시작한다. DMA가 64 B를 넘어 쓰면 guard에서 막히고 TZIC 이벤트가 난다.

### 7.2 Secure 변수 `s_evt_log`의 여정
1. Secure 소스에 `static evt_record_t s_evt_log[8] __attribute__((annotate("guard")));`가 있다. 128 B이고, GTZC 인터럽트 핸들러만 쓴다.
2. **SecureGuardSelect pass**가 판단한다. 0 초기화이고, 128 B ≤ 256이고, 부팅 경로에서 쓰이지 않는다. 설정에서 GTZC 핸들러는 부팅 후에만 켜지는 것으로 지정되어 있다. 그래서 **채택**한다.
3. **배치기**가 NS guard 주소 중 0x2001BB00 블록(Secure 주소 0x3001BB00)에 넣기로 하고, GCC 링커 스크립트에 `.gbind0 : { *(.bss.s_evt_log) } > GUARD0`를 쓴다.
4. **Secure 최종 빌드** 결과, `s_evt_log`의 주소가 0x3001BB00이 된다. 코드는 평소처럼 `s_evt_log[i]`로 접근하고, 추가 비용은 없다.
5. **부팅 시** 검사한다. manifest에 0x2001BB00 guard가 실제로 있으면 블록을 0으로 지우고 사용한다. 없으면 정지한다.

## 8. 자주 묻는 질문

**Q. pass가 잘못 판단하면?**
- **DMA 쪽**: 해석이 불확실한 경우(지역 배열, 힙, 포인터 변수 경유)는 **오류로 멈추고 위치를 알려 준다.** 개발자가 `annotate`로 직접 지정할 수 있다.
- **Secure 쪽**: 기본값이 "표시한 것만 옮김"이고, 판단은 보수적이다. 조금이라도 부팅 중에 쓰일 가능성이 있으면 제외한다.
- 어셈블리 파일(`.S`)에서만 쓰는 변수는 pass가 볼 수 없다. 그런 변수는 설정 파일의 `exclude` 목록에 넣는다(`s_busy` 등).

**Q. 실행 중에 느려지지 않나?**
- 모든 판단과 배치는 **빌드할 때** 끝난다.
- 실행 중에는 변수가 정해진 주소에 있을 뿐이라서 추가 비용이 없다.

**Q. 이 방식이 S-MPU 하드웨어 태깅을 쓸모없게 만들지 않나?**
- 아니다. guard에 Secure 변수를 두는 것은 **"빈 공간의 재사용"**이다. "이 DMA 요청이 허용되는가"를 판단하는 것과는 관계가 없다.
- DMA 권한 판정은 여전히 TTT(S-MPU 태그)와 TTAT(태스크 권한)가 한다.
- 실행 중에 "호출자 → guard"를 찾는 표가 전혀 없다.

**Q. 얼마나 절약되나?**
- 최대 (cluster 수 − 1) × 256 B다. 실제 절약량은 Secure 프로그램에 옮길 만한 작은 `.bss` 변수가 얼마나 있느냐에 달려 있다. `guard_pack_report.txt`에 옮긴 총량이 나온다.

## 9. 용어집

| 용어 | 쉬운 설명 |
|---|---|
| 컴파일 / 링크 | 파일별로 기계어 조각을 만드는 것 / 조각을 합쳐 주소를 정하는 것 |
| 섹션 | 컴파일 결과물 안의 이름 붙은 덩어리. 링커가 이름을 보고 자리를 정한다 |
| 링커 스크립트 | "어떤 섹션을 어느 주소에 둘지" 적은 지시서 (`.ld`) |
| 심볼 | 주소에 붙은 이름 (변수 이름, `__dmac0_start` 등) |
| LLVM IR | 컴파일러 내부의 공통 중간 언어. 분석하기 쉬운 형태 |
| pass | IR을 읽고 판단하거나 고치는 작은 프로그램 |
| 플러그인 | 따로 빌드한 pass 파일(`.so`). 컴파일러나 링커가 실행 중에 불러온다 |
| LTO | 링크할 때 모든 파일의 IR을 합쳐 프로그램 전체를 분석하는 방식 |
| cluster | 한 태스크(또는 공유 그룹)의 DMA 버퍼를 한곳에 모은 영역 |
| guard 블록 | cluster 바로 뒤 256 B Secure 블록. DMA overflow를 막는 벽 |
| S-MPU 태그 | Secure MPU region으로 "DMA 허용 영역"을 표시한 것. TTT 명령이 확인한다 |
| MPCBB | SRAM을 256 B 블록 단위로 Secure/NS 지정하는 하드웨어 (GTZC의 일부) |
| manifest | NS 이미지 안에 있는 cluster/guard 주소 목록. Secure 부팅이 읽는다 |
| implib | NS가 Secure 함수를 부를 때 쓰는 입구(veneer) 주소표 |
| bin-packing | 크기가 다른 짐들을 여러 상자에 최대한 채워 넣는 문제 |
