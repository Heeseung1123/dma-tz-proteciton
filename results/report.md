# 중재자 사이클 측정 보고서

작성일 2026-11-05. 보드 STM32L562E-DK, 8바이트 M2M, N=1000, Task A. DMA IRQ는 측정 구간 동안 항상 차단한다.

표기: [실측] 이번 측정, [코드] 소스/디스어셈블, [도출] 측정값 간 계산, [추정] 근거가 부족한 해석.

## 1. 측정 항목

```
NS   T0 ---- SECURE_dma_m2m_start() 호출 ----------------------------- T5
S          SG, prologue | T1 인자 확인, verify_inst, 레지스터, EN T4 | 복귀, FP 클리어
```

| 항목 | 정의 | 어느 빌드 값인가 |
|---|---|---|
| **start 전체** | T5 − T0. `SECURE_dma_m2m_start` 호출부터 NS 복귀까지 | 타임스탬프 없는 빌드 |
| **내부 (NSC 제외)** | T4 − T1에서 T1·T4 기록 비용을 뺀 값. Secure 진입 후부터 DMA EN 직후까지 | 타임스탬프 빌드 |
| **차분** | start 전체 − 빈 NSC의 중앙값. 내부 값의 교차 확인용 | 타임스탬프 없는 빌드 |
| **verify_inst** | Secure 안에서 호출 전후를 잰 값에서 판독 비용을 뺀 값. BL/BX 포함 | 타임스탬프 없는 빌드 |
| **빈 NSC** | 아무 일도 안 하는 `SECURE_nop3`의 호출~복귀 | 타임스탬프 없는 빌드 |

"내부 NSC 값을 뺀 소모 사이클"은 NSC 진입·복귀 비용을 제외한 값으로 해석했다. 직접 측정이 "내부", 계산값이 "차분"이다.

**start 전체에 ISR은 없다.** DMA IRQ를 막아 두어 전송 완료 처리는 구간이 끝난 뒤에 실행된다.

## 3. 용어

### P1, P2: 컴파일 최적화
| 이름 | Secure | NonSecure | 의미 |
|---|---|---|---|
| P1 | -O0 | -O1 | 현재 프로젝트 기본 설정 |
| P2 | -O1 | -O1 | Secure까지 최적화 |
| P0 | -O0 | -O0 | **미측정.** NS -O0에서 `s_dmaTaskMem` 주소가 바뀌어 Secure 하드코딩과 어긋난다 |

### off, warm, cold: 명령 캐시(ICACHE)
| 이름 | 상태 | 의미 |
|---|---|---|
| off | 꺼짐 | 현재 프로젝트 설정. 매번 플래시에서 읽는다 |
| warm | 켜짐, 채워진 상태 | 같은 코드를 반복 실행할 때. 가장 빠르다 |
| cold | 켜짐, 매 회 비움 | 오랜만에 실행하는 코드와 비슷하다. 캐시를 채우는 비용까지 들어 off보다 느릴 수 있다 |

### wait state (WS)
플래시는 CPU보다 느려서 읽는 동안 CPU가 기다린다. 이 대기 사이클 수가 wait state다. `FLASH_ACR` 레지스터의 LATENCY 값으로 정한다.

### 판독·기록 비용 (보정값)
사이클을 재는 동작 자체도 사이클을 쓴다. 사이에 아무것도 없이 같은 코드로 재서 그 값을 뺀다. 측정 코드도 플래시에서 실행되므로 조건마다 값이 다르다.

## 4. 110MHz와 32MHz에서 사이클이 다른 이유

**CPU 사이클 수는 같아야 하지만, 플래시 대기 사이클이 클럭에 따라 달라지기 때문이다.** 플래시 읽기는 클럭과 상관없이 비슷한 시간이 걸리므로, 클럭이 높을수록 그 시간이 더 많은 사이클이 된다.

| 클럭 | FLASH_ACR [실측] | 플래시 1회 읽기 | 실제 시간 [도출] |
|---|---|---|---|
| 110MHz | 5 WS | 6 사이클 | 약 54.5ns |
| 32MHz | 1 WS | 2 사이클 | 약 62.5ns |

**확인:** 플래시를 거의 읽지 않는 warm에서는 두 클럭의 값이 거의 같다 [실측].

| P1 | verify_inst | 빈 NSC | start 전체 |
|---|---|---|---|
| 110MHz off | 62 | 162 | 374 |
| 32MHz off | 28 | 73 | 182 |
| 110MHz warm | 21 | 59 | 164 |
| 32MHz warm | 21 | 59 | 151 |

**사이클이 적다고 더 빠른 것은 아니다.** P1 off의 start 전체는 110MHz에서 374 사이클(약 3.4µs), 32MHz에서 182 사이클(약 5.7µs)이다 [도출].

32MHz 측정의 1 WS는 이번 측정에서 정한 값이다. D-Box 보드의 설정은 논문에 없다.

## 5. 코드가 어떻게 돌아가는가

**측정 코드 위치**

| 파일 | 역할 |
|---|---|
| `project/NonSecure/Src/bench_ns.inc` | 측정 순서와 결과 표. 맨 위 설명부터 읽으면 된다 |
| `project/Secure/Src/bench_s.inc` | Secure 측정 함수 (내부 값 반환, verify_inst, IRQ 차단, 캐시 비움) |
| `secure_nsc.c`의 `BENCH_T1()`, `BENCH_T4()` | 중재자 안의 기록 지점. `BENCH_TS` 빌드에서만 코드가 생긴다 |
| `scripts/eval/` | 빌드, flash, 회수, 집계 |

**한 번의 측정** (`bench_start_once`)
1. `SECURE_bench_irq_mask(1)`: DMA IRQ 차단.
2. T0 판독 → `SECURE_dma_m2m_start()` → T5 판독.
3. `SECURE_bench_irq_mask(0)`: 여기서 ISR이 돌아 전송 완료를 처리한다.
4. `SECURE_bench_inner()`로 T4 − T1을 받아 표에 기록한다.

**전체 흐름**
1. `Bench_Main`이 테스트 6개를 차례로 1000회씩 실행한다: NS 판독, 빈 NSC, start, T1·T4 기록 비용, verify_inst, verify 판독 비용.
2. 테스트마다 SRAM2에 표를 쓰고 `bench_hit()`을 부른다. gdb(`run_bench.py`)가 여기서 멈춰 CSV로 옮긴다.
3. `run_all.sh`가 조건마다 빌드, flash, 측정을 반복한다. `analyze.py`가 표를 만든다.

**빌드 매크로**: `BENCH_PHASE`(측정 코드 포함), `BENCH_TS`(T1·T4 기록), `BENCH_ICACHE`(캐시 켬), `BENCH_COLD`(매 회 캐시 비움), `BENCH_CLK_32M`(32MHz), `BENCH_N`(반복 수).

**start 전체와 내부를 다른 빌드에서 재는 이유**: T1·T4 기록이 start 전체를 늘린다(P1 110MHz off 374 → 423 [실측]). 그래서 start 전체는 기록이 없는 빌드 값을 쓴다.

**기본 빌드는 이전과 동일하다** [실측]: 매크로를 모두 끈 빌드는 원본 커밋 9679590과 `verify_inst`, 중재자, 두 핸들러의 디스어셈블과 NS 코드가 같고, 보드에서 statMediator 828, statRoundtrip 841을 낸다. 828은 DMA IRQ를 막지 않은 기존 측정값이다.

## 6. 값의 의미

- **D-Box 비교:** D-Box validation은 569 / 657 / 792다 (32MHz, Cortex-M3). 같은 클럭의 캐시 off 값은 verify_inst 28, 내부 101, start 전체 182다. 코어, 측정 경계, 검증 내용이 달라 배수로 비교할 수는 없다. 상세 기준값은 `docs/dbox_reference.md`.
- **논문 표 2:** P1 110MHz warm의 start 전체 164, 빈 NSC 59는 논문의 160, 66에 가깝다. 현재 코드는 논문의 TTT×2보다 TTAT 2개가 많다. 이전 측정에서 그 몫은 warm 기준 약 7이었으므로 TTT×2로 환산하면 약 157이다 [도출, TTAT 몫은 이번에 다시 재지 않음]. 논문 측정 당시의 ICACHE·IRQ 조건은 미확인이다.

**이전 값과의 차이:** 이전 측정의 P1 warm IRQ 차단값은 204였고 이번은 164다. 하니스가 달라 코드 배치와 측정 사이에 실행되는 코드가 바뀌었다. 캐시가 1-way 설정이어서 충돌이 달라졌을 수 있다 [추정, 확인 안 함]. warm 값은 코드 배치에 민감하므로, 40 사이클 정도의 차이는 기법의 차이로 해석하면 안 된다. off 조건은 369와 374로 거의 같다.
